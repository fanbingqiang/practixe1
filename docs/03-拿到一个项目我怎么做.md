# 拿到一个项目，我会怎么做 —— 思维框架与操作手册

> 适用场景：入职接手老项目、接手中途项目、临时救火、接手别人跑路的项目
> 核心心法：**先搞清是什么 → 再让它跑起来 → 然后画地图 → 建安全网 → 小步改动 → 交付复盘**
> 一句话总结：**不要想读完代码再动手，你会淹死；也不要没跑起来就改代码，你会更惨。**

---

## 零、先建立正确的心态（比技术重要）

| 错误心态 | 后果 | 正确心态 |
|---------|------|---------|
| "我要先把代码全部读完" | 几万行代码，读三天还没动手，越读越慌 | **只读你要走的那条路径**，其余先跳过 |
| "这代码写得太烂了，我想重写" | 重写 90% 会失败，且会引入未知数量新 bug | **先让它能跑、能被验证**，再谈改进 |
| "我看懂了，应该没问题" | "应该"是事故的起点 | **跑一次，用真实输出说话** |
| "先改起来，边改边看" | 改乱了不知道哪一步错的 | **改动前先建安全网** |
| 一次性改十个文件 | 出问题无法定位是哪一处 | **一次只改一件事，改完立刻验证** |

**判断你有没有真懂一个项目，就一条标准**：
> 你能不能用一段话，把"一个请求从进来到返回，中间经过了哪些环节、数据存到哪"讲清楚。
> 讲不清楚 = 还没懂，继续画地图。

## 一、第一阶段：搞清"这是什么"（不动一行代码）

### 1.1 先问 6 个问题（问人，比读代码快 10 倍）

1. **这个系统解决什么问题？谁在用？**
   —— 不知道业务目标，就无法判断什么改动是"对的"
2. **它现在跑在哪？有几个环境？**（dev / test / prod 各有几套）
   —— 关系到你敢不敢动、怎么验证
3. **我这次的任务是什么？**改 bug / 加功能 / 重构 / 救火？
   —— 任务不同，策略完全不同（救火时不要顺手重构）
4. **谁最懂它？我能问谁？**
   —— 老同事的十分钟，抵你自己摸索一天
5. **有文档吗？文档可信吗？**
   —— **文档通常滞后于代码**，以代码为准，文档当线索
6. **改动会影响谁？**（上下游系统、其他团队、前端、数据报表）
   —— 影响面决定你的验证范围

> 这 6 个问题答不出来，就别急着看代码。**先搞清"为什么"，再搞"怎么做"。**

### 1.2 然后看这 7 样东西（按优先级，30 分钟内完成）

| 顺序 | 看什么 | 想从中得到什么 |
|------|--------|---------------|
| 1 | `README.md`、`docs/` | 项目是干嘛的、怎么启动、已知坑 |
| 2 | `pom.xml` / `build.gradle` | **技术栈与版本**：Spring Boot 几？JDK 几？用了哪些库？ |
| 3 | 配置文件（`application.yml`、`.env`） | **依赖哪些外部系统**（DB/Redis/MQ/第三方）、端口、环境差异 |
| 4 | 启动类 / `main` 函数 | 程序从哪进、开了哪些功能开关 |
| 5 | 目录结构 | **分层方式**（controller/service/dao…），有没有多模块 |
| 6 | `git log --stat -20` | **谁在动哪些文件** —— 改动最频繁的文件就是核心/高风险区 |
| 7 | 测试目录 | 有多少测试、测什么、**能不能跑通**（决定你有没有安全网） |

### 1.3 看历史的技巧（很多人忽略）

```bash
git log --oneline -20                    # 最近在干什么
git log --stat -20                       # 哪些文件被改得最多 = 核心区
git shortlog -sn                         # 谁提交最多 = 该找谁问
git log --oneline --since="3 months ago" # 近期活跃度
grep -rn "TODO\|FIXME\|HACK\|XXX" src/   # 前人留下的坑
```

**为什么这招好用**：频繁改动的文件 = 业务核心 + 容易出问题的地方。
改这些文件之前，先看它过去被改坏的记录（`git log -p <file>`）。

## 二、第二阶段：让它跑起来（能跑 = 能验证 = 有底气）

> **跑不起来，你的一切理解都是纸上谈兵。**
> 这是新人最容易卡住、也最容易放弃的一步——但恰恰是必须迈过的坎。

### 2.1 三件事必须先确认

```
① 依赖服务从哪来    → MySQL/Redis 是自己装、Docker、还是连测试环境？
② 配置怎么给        → 密码/密钥在哪？有没有 .env.example 或文档？
③ 怎么启动          → java -jar？mvn spring-boot:run？IDEA 运行？
```

### 2.2 跑起来的正确顺序（不要跳步）

```
1. 编译通过          mvn clean compile
2. 测试通过          mvn test          ← 先看现状，红了先记下来，别急着修
3. 启动成功          mvn spring-boot:run
4. 打一个真实请求      curl / Apifox     ← 这一步必须做！
```

**第 4 步是分水岭**：容器启动 ≠ 功能可用。必须真的发一个请求、拿到真实响应。

### 2.3 跑不起来时的排错顺序（我们真实经历过）

| 症状 | 排查方向 | 真实案例 |
|------|---------|---------|
| 依赖下载失败 | 仓库路径、镜像、网络、代理 | 我们踩过：Maven 配置指向了不可写目录（见 `03-故障复盘-BUG-001.md`） |
| 编译不过 | JDK 版本、依赖冲突（`mvn dependency:tree`） | — |
| 测试报奇怪的初始化错误 | 环境限制、agent、时区 | 我们踩过：Mockito 需要 JVM attach，受限环境禁止 |
| 启动报 Bean 冲突/找不到 | 配置文件、扫描路径 | — |
| 启动成功但请求 404/500 | 端口、context-path、日志里的第一条 ERROR | — |

**排错心法（三句话）**
1. **先读 `Caused by`**，最外层异常往往是噪音
2. **先证伪，再动手**：怀疑网络就单独测网络，怀疑配置就单独看配置
3. **跑一次不算数**：修复后连续跑两次，排除偶发

## 三、第三阶段：画地图（把项目变成你自己的）

### 3.1 三条线，画完就算懂了一半

| 线 | 要回答的问题 | 怎么画 |
|----|-------------|--------|
| **调用链** | 一个请求从哪进、经过哪些类、从哪出？ | 从 Controller 出发，跟一个真实请求走到底 |
| **数据流** | 数据从哪来、存到哪张表、中间怎么变？ | 从实体类找表名，从 Mapper 找 SQL |
| **依赖线** | 依赖哪些外部系统？挂了会怎样？ | 看配置 + 代码里的第三方 SDK |

### 3.2 读代码的正确姿势（关键差异）

**❌ 错误做法**：从 `src/main/java` 第一个文件开始，一个一个往下读。
**✅ 正确做法**：

1. 找**入口**（Controller / 定时任务 / MQ 监听器）
2. 挑**一个最简单的接口**，只跟着它走完整条链路
3. 遇到不认识的类名**先记在纸上，不要停下来读**
4. 走完一条链，你对项目的理解会超过读 100 个文件
5. 然后换第二条链，重复

**为什么这样有效**：代码是图，不是线性文本。
**跟着一条真实路径走，就把这张图的一条边全点亮了。**

### 3.3 产出物：一份自己的《项目地图》

必须写下来。**能写清楚才算真懂**，而且这份文档会成为你后续所有工作的索引。
内容至少包含：
- 技术栈与版本
- 目录/分层结构
- **至少 3 条完整调用链**（普通查询 / 写操作 / 异常路径）
- 依赖的外部系统清单
- 已知的坑与坑位（带证据）
- 我不确定、需要问人的问题清单

## 四、第四阶段：建安全网（改动之前，必须先有网）

**没有安全网就改代码 = 高空作业不系绳。**

| 安全网 | 怎么做 | 作用 |
|--------|--------|------|
| 测试 | 能跑的先跑一遍；没测试的，**先写一个"描述当前行为"的测试** | 改坏了立刻知道 |
| 分支 | `git switch -c feature/xxx`，绝不在主干上直接改 | 改废了能一键丢弃 |
| 小步提交 | 一件事一个提交 | 出问题能精准回滚 |
| 日志 | 关键路径加日志（带 traceId） | 出问题能看见 |
| 备份 | 动数据库前先备份 | 数据没了就真没了 |

**特别提示**：给老代码补测试时，**先写"现状测试"**（把当前行为固化下来），
哪怕当前行为是错的。先锁住现状，再改，才能看出你改了什么。

## 五、第五阶段：小步改动（先打通，再完善）

### 5.1 用"曳光弹"思路（Tracer Bullet）

> 不要一次做完整个功能。先做**最薄的一层**，从入口打通到出口，
> 确认整条链路是活的，再往上加逻辑。

例：要做一个"下单"功能
```
第 1 步：接口能返回一个假的订单号（打通链路）
第 2 步：接上数据库，能真的插一条记录
第 3 步：加业务校验（库存、金额）
第 4 步：加事务、加幂等
第 5 步：加缓存、加异步
```
每一步都**可运行、可验证**。出问题只在最后一步的改动范围里找。

### 5.2 每次改动的循环

```
改一处 → 跑测试 → 打真实请求 → 看日志 → 提交 → 下一处
```

### 5.3 提交信息要能当"事故档案"

```
feat(order): 新增创建订单接口
fix(order): 修复金额精度丢失（用 double 改 BigDecimal）
```
半年后有人查"这个金额为什么这么算"，靠的就是这些提交信息。

## 六、第六阶段：交付（让别人敢用你的东西）

| 项 | 内容 |
|----|------|
| 自测证据 | 测试命令 + 真实输出，不发"应该没问题" |
| 文档同步 | 接口文档、部署文档、README 该改就改（**改默认值 = 改契约**） |
| 变更说明 | 影响面、是否破坏性变更、**回滚方式** |
| 上线检查 | 数据库脚本、配置、监控、备份 |
| 复盘 | 出过的问题写成记录，下次不再踩 |

## 七、一页纸 SOP（打印贴墙上）

```
【0】心态：不读完再动手，不没跑就改，一次只改一件事

【1】搞清是什么（30 分钟，不动代码）
    □ 问 6 个问题（业务/环境/任务/老同事/文档/影响面）
    □ 看 README、pom、配置、启动类、目录结构
    □ git log --stat -20  找热点文件
    □ 看测试目录

【2】让它跑起来
    □ 编译 → 测试 → 启动 → 打真实请求
    □ 跑不起来的排错：先读 Caused by，先证伪再动手
    □ 修复后连跑两次，排除偶发

【3】画地图（产出《项目地图》文档）
    □ 调用链 ≥ 3 条（读操作 / 写操作 / 异常路径）
    □ 数据流：表结构、关键字段
    □ 依赖线：外部系统清单
    □ 已知坑 + 待确认问题清单

【4】建安全网
    □ 跑通现有测试
    □ 没测试的关键路径，先补"现状测试"
    □ 开分支，绝不在主干上直接改

【5】小步改动
    □ 先打通最薄的一层链路
    □ 每次只改一件事，改完立刻验证
    □ 一件事一个提交

【6】交付
    □ 测试证据（真实输出）
    □ 文档同步
    □ 变更说明 + 回滚方案
    □ 复盘记录
```

## 八、新人常犯的 7 个错（对照检查）

1. ❌ 想先读完所有代码 → 淹死在细节里
2. ❌ 项目没跑起来就开始改 → 改了也不知道对错
3. ❌ 上来就想重构 → 90% 失败，还会引入新 bug
4. ❌ 一次改十个文件 → 出问题无法定位
5. ❌ 用"我觉得""应该"做判断 → 必须用真实输出验证
6. ❌ 不看 git 历史 → 错过了"这里以前出过事"的警告
7. ❌ 不记录 → 同样的问题会再踩第二次

---

## 九、这套方法论在我们项目里的实际应用

接下来我会用 `practice-order` 当"**你刚入职接手的项目**"，
把上面第 1~3 阶段完整走一遍，产出一份真实的《项目地图》作为示范。

**你以后接手任何项目，都可以照着这份 SOP 走。**
